## 2. C1 — attempted, DISCARDED, and why

The plan's zero-build discriminator turned out to be better-founded than expected:
`Capture_Data_Bits` (Receiver.v:373) consumes `QPSK_Rx_dataOut`, **upstream of the entire
byte plane**, and drives `packets_out` (0x104) / `bit_errors_out` (0x108). That is a
free T1-equivalent tap — but only meaningful when the transmitter radiates the known ROM.

The run returned BER 5.27e-3 (59 errors/frame). **Discarded, not reported as a finding**,
for two reasons: no validity control (the BIST reference is a compiled-in message; a
mid-range BER is equally consistent with real errors and a partial reference mismatch),
and the link was degraded during the window (479 fps against 1245). `c1b_bist_controlled.sh`
is written and holds both arms — ROM (reference should match) and host-bytes (reference
*cannot* match, the planted fault) — and has not been run on a healthy link yet.

**Method error to not repeat:** the C1 restore wrote `0x158=1` directly to 146. Bringup
warns that flipping the byte source before the daemon's TX stream is flowing starts the
modulator mid-stream; carrier-reset churn followed. Source-mux changes go through
bringup's sequencing, never an ad-hoc poke.

## 3. The 148 byte-plane wedge — characterized, and a fix validated in the failure

**Signature:** modem decoding at full line rate (`0x104` +1240/s, framesync 1251, **zero**
carrier resets) with the fabric byte counter `0x1C0` **completely frozen**; host at
`dma_rx_ok=2` while `crc_drop` climbed ~25k/window and `idle_rx` sat frozen.

`0x1C0` counts beats accepted as `valid && ready`. The ring had stopped re-submitting, so
`byte_rx_ready` stayed low, no beat was ever accepted, and the host re-consumed **stale
buffers** forever — counting them as CRC failures, which is why it looked busy.

**Localization, corrected twice.** An early daemon restart cleared it, so it was called
host-side; a later restart did **not**, and a `0x000` fabric soft reset did not either
(`0x1C0` reset to 0 and stayed there while `0x104` climbed to 11825 — modem re-locked,
DMA still never ready). Accurate statement: the stuck element is on the **DMA/ready side
of the byte handoff and survives both reset paths**.

**Root cause (structural, provable by reading):** the queued-RX watchdog lived at step 4 of
`rx_pump_queued`, but step 3 (`rx_done_q` → `rx_q_on_complete` → `return 0`) returns on
every call while bogus completions arrive, so the timeout check was **unreachable**.
`rx_q_progress` is only stamped on a delivered frame, so the timeout had long expired —
the code never looked. *A stream of empty completions starved its own watchdog.*

**Validation in the failure state:** the patched daemon was deployed into the live wedge,
after it had already survived an unpatched restart AND a fabric reset. It logged exactly
one `no DELIVERY for 3.0s -- re-arming` and `0x1C0` resumed at **237,776 words/s** =
line rate (191 × 1245 = 237,795). One re-arm, no thrashing. Deployed to both boards.

## 4. A pattern worth acting on: guards that watch a signal alive during their own fault

Three instances found in two days — all fixed:

1. **skid v2 witness** — keyed on TLAST/TUSER, and `-M` production mode carries neither
   (`tlast_en=0`; TUSER never fires). Blind by construction. Measured over 6689 samples.
2. **`lock_watchdog` HOST-WEDGE** — tripped only if `idle_rx + dma_rx_ok` froze, but
   `idle_rx` counts *idle* pump calls and increments continuously during the wedge. Now
   keys on `dma_rx_ok` alone, plus a new register-based `0x1C0`-frozen detector.
3. **`qpsk_tun` queued-RX watchdog** — unreachable code path (above).

Recommendation: audit the remaining guards for the same shape — *does the signal this
guard watches keep moving during the failure it is meant to detect?*
