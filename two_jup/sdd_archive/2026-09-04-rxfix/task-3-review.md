# Task 3 (T0c) review — slackleg_go.sh / witness_read.sh (commit d34e530)

**Verdict: CONDITIONAL PASS** — netlist citations and DRY/test discipline are solid, but the 146 timed-poke has an unverified/likely-late timing assumption and the SIGTERM-mid-window restore path has a real race that lets the trap-guarded restore be silently overwritten. Fix before this is used for T1's real A/B leg.

## Critical
- **`two_jup/rxfix/slackleg_go.sh:118-135` (`peer_poke_bg`) races `restore()` on SIGTERM/kill.** `trap restore EXIT INT TERM` (line 96) is registered before `peer_poke_bg` is backgrounded, but `restore()` never references `$PEER_PID` — it doesn't kill or wait on the peer-poke watcher before writing `0x208=0x0` to 146. On a normal exit the script explicitly does `wait "$PEER_PID"` then calls `restore()` (safe), but on a mid-window `systemd stop` (SIGTERM via `launch_rig_unit.sh`, `TimeoutStopSec=600`) the trap fires immediately and races the backgrounded `146 fixctl=$FIXVAL` write in flight or still asleep in `sleep "$WAIT_146"`. If systemd's default `KillMode=control-group` doesn't land both signals atomically (or the peer's `ssh` command has already been dispatched to the remote shell before the local process is killed), 146 can end up left at `fixctl=0x8` (enSlack ON) even though `meta.txt` reports `fixctl_restored=1`. This is exactly the scenario the review brief asked to check, and it is not mitigated: `restore()` should `kill "$PEER_PID" 2>/dev/null` (and ideally re-issue the 146 clear *after* joining it) before declaring restored.
- **`test_slackleg_dry_restore_ordering_is_146_then_148_and_trap_fires_on_term` (`two_jup/tests/test_rxfix_rig_scripts.py:157-196`) does not exercise this race.** In DRY mode `peer_poke_bg` is never launched (`PEER_PID=""`, real branch only runs when `DRY=0`), so the TERM test's docstring claim ("prove this by sending TERM... trap fires even when killed mid-run") is not actually testing the peer-write race — it only proves the trap prints a restore verdict when nothing was racing it. The one scenario the brief called out is untested by design of the DRY-only harness; that's an acceptable gap for a DRY-only task, but the report should say so explicitly instead of implying the TERM path is covered.

## Important
- **The "matches radioprobe_go.sh's model" claim is not accurate.** `slackleg_go.sh:37-38` and `task-3-report.md` both justify `WAIT_146=20` as "matching radioprobe_go.sh's model." `two_jup/comb/radioprobe_go.sh` has no `sleep`/`wait`/timed-poke logic anywhere (`grep -n "sleep\|wait\|WAIT"` returns nothing) — its peer-board probe (PROBE=D) lands via `capture_r3.sh`'s in-script `PEER_ATTR_POKE` hook (section 5d), at a fixed position in `capture_r3.sh`'s own timeline, not via an external sleep-then-write from the wrapper. There is no existing precedent in this codebase for a 20 s external-timed poke; the number is asserted, not derived or measured.
- **WAIT_146=20 s is not shown to land before the window opens, and plausibly does not.** Walking `capture_r3.sh` from the `"wedge verdict:"` line (198) to the point the scored window actually starts (the stall-watchdog loop at line ~319, which is effectively the acceptance window per the `CAP_SETTLE` comment at 281-287 — PER acceptance starts at `t>=15s` post-rotate): LOOP_POKE (~1 ssh RTT) → framelog rotate + `sleep 1` → `snap`+`sleep 2`+`snap` → Tap-A `iio_readdev` (NSAMP=4,000,000 samples ≈ 65 ms of device time, plus ssh RTT) is roughly 4 ssh round-trips and ~3 s of sleeps — plausibly under 15 s total, i.e. inside the `t>=15s` PER-acceptance boundary the survey already treats as "steady state." A `WAIT_146=20` write could land *after* the window has already opened, meaning part of the scored window runs with 146 still at the old fixctl value — not a clean A/B split, contradicting the requirement this review was asked to confirm. Nothing in the deliverable computes or bounds this; it should either shrink `WAIT_146` with a measured margin, or (better) have the leg log a distinguishable "peer poke landed at Ts, window opened at Tw" pair so a real T1 run can be audited after the fact instead of trusted blind.
