## The day's headline: the loss budget has been re-attributed

Three independent lines of evidence, produced today, converge on the **TX byte path**:

1. **Anchor re-derivation** (`tap_replay_study/ANCHOR_REDERIVED.md`): the two netlist
   "CRC failures" (k=300/330) are frames whose transmitted payload is **all zeros in
   the air** (191/191 zero words, verified at two chunk alignments — I spot-checked
   independently). Every hardware-lost seq that was actually aired decodes CRC-good.
   Two seqs (53878, 53899–53900) were **never transmitted** (TX seq skips). There is
   NO demonstrated RX demod/decision failure on this capture. The old "isolated loss /
   phase step" class is TX-side.
2. **Envelope scan, 4 captures** (`two_jup/TX_ANOMALY_SCAN.md`): zero-payload events
   in every capture — hunt_auto 2, cfo0 6, rxq_M32 1 (the "clean" capture was a window
   artifact), revlong 23 — **exactly integer-periodic** (30/33/34 frames), **fixed
   start phase per capture** (e.g. start mod frame = 39756 both hunt_auto events),
   two length classes (~1 and ~0.5 frame), always full carrier amplitude (constant
   envelope = repeated symbol; never an RF mute). Deterministic TX buffer-wrap/
   underrun zero-fill, rate-dependent. Reverse ~10x worse — matches (and explains)
   the old §5 direction asymmetry.
3. **Wedge checkpoints, 4/4 reproductions** (`wedgeck_20260812_095205`, harness
   `two_jup/wedge_ckpt.sh`, instrument = CP2/CP3 seam checkpoints now in qpsk_tun,
   QPSK_CKPT): in-wedge, **CP2 advances and CP2==CP3 with zero mismatches** — the RX
   DMA seam and the carve→host copy are exonerated. Framesync degrades to ~254–273/s
   (vs 1245), rstcs stays 0, and the delivered content fails PN ("junk", NOT zeros —
   dense pseudo-random; classification agent running). In loopback there is no
   channel, so the corruption is upstream of the RX DMA write: TX side or demod.

Remaining separate class: the **26-frame burst** = RX host delivery stall — now
